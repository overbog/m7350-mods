# Administrative shell over USB from OEM

Tested on a TP-Link M7350(EU) v5.2 with OEM firmware **1.0.10 Build 181220 Rel.1066n** and its stock web interface. Start with the router powered on in OEM and the current web-admin password. A password reset, firmware image, preinstalled SSH server, device key or previous installation of this project is unnecessary. Use this procedure only on a device you administer.

The stock authenticated Port Trigger handler on this build can execute a command. The helper uses it to open a temporary root Telnet listener, then removes the rule and stops the listener. Telnet exposes an unauthenticated shell. Disconnect Wi-Fi clients, prevent them from joining during the maintenance window, and keep the USB network off other LANs. The listener binds the router's LAN address, which can also be reached from its own Wi-Fi. The technique is described in the [EFF Rayhunter M7350 notes](https://github.com/EFForg/rayhunter/blob/7ce6f35991b47f5e2dff8c79399f4fc5f5bb981b/doc/tplink-m7350.md#port-triggers). This procedure uses a separate rule name and does not install Rayhunter.

## From cable to root shell

1. Connect a USB **data** cable to a Linux host and turn the router on. If using a VM, pass the USB device to the VM first. Verify the normal USB identity with `lsusb -d 2357:0005` and look for `rndis_host` in `lsusb -t`. Find the RNDIS interface with `ip -br link`. An OEM login page reached on that interface is the readiness check if the screen shows only charging or USB is still enumerating.
2. Give the interface an address on the factory LAN. Use a DHCP lease or choose an unused address such as `192.168.0.2/24` on an isolated link. Configure no default route on USB for this operation. For example, on a host where `lte0` is the USB interface and it has no address yet, run `sudo ip link set lte0 up` and `sudo ip addr add 192.168.0.2/24 dev lte0`. Replace `lte0` with the actual interface in all commands. Check that `ip -4 route get 192.168.0.1` names that interface, with no gateway and with the USB IPv4 address as source. If the host already has another route to the same subnet, isolate the USB link in a Linux VM or resolve the route conflict before continuing.
3. Verify OEM HTTP using `curl --noproxy '*' --interface lte0 -fsS -o /dev/null -w '%{http_code}\n' http://192.168.0.1/login.html`. Expect 200. Reserve one OEM admin session for this procedure. The helper checks the stock web fingerprint, that TCP 22, 23 and 2222 explicitly refuse connections, and that the router reports no associated clients and an empty Port Trigger list. Use a unit with an empty list for this procedure. Existing rules require separate handling and are left in place.
4. From this checkout, run `python3 tools/oem-usb-shell.py lte0` for a bounded check, or `python3 tools/oem-usb-shell.py lte0 --shell` to use the shell. Interactive mode requires GNU Inetutils Telnet (`inetutils-telnet` on Debian). Enter the existing OEM admin password at the hidden terminal prompt. Once the temporary listener answers, the helper verifies `id -u` returns `0` and reads the boot ID.
5. In interactive mode the temporary rule is removed before the terminal session is handed to you. Keep the helper running while using the shell. Type `exit` when done. The helper verifies the listener's exact process identity before terminating it, checks TCP 23 refusal, and rereads authenticated OEM status and the Port Trigger list. Successful verification ends with `PASS: OEM status, original empty Port Trigger list, TCP 23 closed`.

## If the session is interrupted

Keep the router isolated and independently verify both the OEM Port Trigger list and TCP 23. In the OEM interface under **Advanced → NAT Forwarding → Port Triggering**, remove only the entry named `m7350-usb-shell` if present. Reload the page to confirm its removal. Deleting the rule can leave the listener running. If TCP 23 still accepts connections, identify its PID from `netstat -lntp` in the existing administrative shell, check that `/proc/<PID>/cmdline` is exactly `busybox telnetd -b 192.168.0.1 -l /bin/sh` with NUL-separated arguments, then send SIGTERM to that PID. If the shell is unavailable, use a normal OEM reboot after confirming rule removal. Recheck explicit refusal on TCP 23 and OEM login over RNDIS before reconnecting clients.

## Physical test result

**2026-11-16.** Started with the verified stock web bundle, an empty Port Trigger list, and TCP 22, 23 and 2222 refusing connections. A Debian staging VM enumerated `2357:0005` and bound `rndis_host`. The USB interface already had a direct IPv4 management route. The test used the current OEM password, first through protected input and then through the helper's hidden terminal prompt.

Both the bounded probe and a new interactive session obtained UID 0 over USB. The interactive client ran `id -u` and exited. The original boot ID remained the same across the successful probes. During development, rule deletion succeeded on the first root-shell probe but `pidof telnetd` missed the listener because the process was named `busybox`. The listener was stopped by its verified PID. The helper now obtains that PID from the listening socket and checks the command line. Both final probes verified cleanup.

An independent check after the last probe verified the OEM web fingerprint, authenticated status, an empty Port Trigger list and explicit refusal on TCP 22, 23 and 2222. The router was left in OEM. This was a configured stock router, with no factory reset, firmware flash, VPN installation or reboot during this test.
